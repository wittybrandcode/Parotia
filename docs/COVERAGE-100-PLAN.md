# خطة الوصول إلى تغطية اختبارية 100% في Parotia

> وثيقة تنفيذية لرفع تغطية الكود القابل للتنفيذ إلى 100% دون استبعادات مضللة أو اختبارات شكلية، مع الحفاظ على ثبات سلوك الإضافة.

| البيان | القيمة |
|---|---|
| تاريخ خط الأساس | 2026-08-26 |
| النطاق | `src/**/*.ts` و`src/**/*.tsx` بعد تدقيق الملفات غير التنفيذية |
| أداة القياس | Vitest + V8 Coverage |
| الاختبارات الحالية | 441 اختباراً في 48 ملفاً + 5 اختبارات Playwright |
| حالة الخطة | قيد التنفيذ — C0 مكتملة محلياً وC1 مكتملة عدا فروع `shortcuts.ts` |
| الهدف النهائي | 100% Lines / Statements / Functions / Branches |

## 1. الهدف التنفيذي

الوصول إلى تغطية حقيقية مقدارها 100% لكل الكود التنفيذي المشمول، بحيث يثبت كل اختبار سلوكاً أو عقداً أو مسار فشل له قيمة، ولا يكتفي بتنفيذ السطر لرفع الرقم.

تُعد الخطة مكتملة فقط عندما:

1. تسجل المقاييس الأربعة 100%: الأسطر، التعليمات، الدوال والفروع.
2. تنجح اختبارات الوحدة والتكامل واختبارات Chromium الحقيقية.
3. لا يُستخدم `/* istanbul ignore */` أو `/* v8 ignore */` لإخفاء كود قابل للاختبار.
4. لا تُستبعد ملفات تنفيذية لمجرد صعوبة اختبارها.
5. تبقى بوابات TypeScript وESLint والأمان والبناء ناجحة.
6. لا تتغير الوظائف الحالية إلا عند اكتشاف عيب موثّق باختبار انحدار.

## 3. سياسة النطاق ومنع التلاعب

### 3.1 ما يدخل في القياس

- كل وحدة تحتوي قراراً أو أثراً تنفيذياً داخل `src/`.
- جميع مسارات النجاح والفشل والإلغاء والمهلة الزمنية.
- تكاملات Chrome التي يمكن تمثيلها بعقود mocks دقيقة.
- سلوك DOM وCanvas الذي يمكن اختباره في Happy DOM أو Chromium.
- معالجات React، حتى عندما تكون قصيرة أو معرفة داخل JSX.

### 3.2 الاستبعادات المقبولة

لا يُقبل الاستبعاد إلا إذا كان الملف لا يضيف أي قرار تنفيذي مستقل:

| الملف | القرار المقترح | السبب | التعويض |
|---|---|---|---|
| `src/ui/src/editor/main.tsx` | استبعاده من Unit Coverage | نقطة Mount تصريحية فقط، مماثلة لـ`src/ui/src/main.tsx` المستبعد حالياً | إثبات إقلاع المحرر في Playwright |
| `src/content/handlers/types.ts` | استبعاده | أنواع TypeScript فقط؛ لا توجد تعليمات تنفيذية | يظل خاضعاً لـTypeScript |

بعد تدقيق النطاق وتنفيذ الدفعة الأولى أصبحت النتيجة الرسمية 91.23% للأسطر والتعليمات، و84.79% للدوال، و79.24% للفروع. تظل الأرقام الأصلية أعلاه خط الأساس المرجعي الذي يمنع الحارس الآلي الرجوع دونه.

### 3.3 استبعادات ممنوعة

- استبعاد ملف لأنه يعتمد على Chrome أو Canvas.
- تجاهل فرع خطأ يمكن حقنه باختبار.
- كتابة اختبار لا يحتوي assertion سلوكي واضح.
- اختبار تفاصيل React الداخلية بدلاً من النتيجة المرئية أو الأمر الصادر.
- تغيير الكود إلى شكل أسهل للتغطية دون مكسب تصميمي أو سلوكي.

## 4. نظام التتبع

### حالات العمل

| الرمز | الحالة | الاستخدام |
|---|---|---|
| `[ ]` | لم يبدأ | لا يوجد تنفيذ بعد |
| `[-]` | قيد التنفيذ | توجد تغييرات محلية لم تجتز كل البوابات |
| `[~]` | مكتمل محلياً | نجحت الاختبارات المحلية وينتظر المراجعة أو الدمج |
| `[x]` | مكتمل | مدمج واجتاز CI |
| `[!]` | متعطل | يحتاج قراراً موثقاً أو تغييراً في بيئة الاختبار |

### الحقول الإلزامية عند تحديث أي بند

- الحالة.
- رابط الاختبار أو اسم ملفه.
- نسبة الملف قبل التنفيذ وبعده.
- عدد الاختبارات المضافة.
- بوابات التحقق التي نجحت.
- أي عيب إنتاجي اكتُشف أثناء كتابة الاختبار.

يجب أن يغطي كل عقد مناسب الحالات التالية:

| البعد | الحالات الدنيا |
|---|---|
| النتيجة | نجاح، فشل متوقع، فشل غير متوقع، إلغاء |
| البيانات | صحيحة، فارغة، حدود دنيا/عليا، تالفة |
| التوقيت | فوري، async، timeout، race، re-entry |
| الملكية | جلسة صحيحة، جلسة غائبة، sender/tab/token غير مطابق |

ليست كل خلية مطلوبة لكل دالة؛ المطلوب اختيار الخلايا التي تمثل فرعاً فعلياً في عقدها.

## 8. قواعد جودة الاختبار

1. اسم الاختبار يصف invariant واضحاً، لا اسم الدالة فقط.
2. كل إصلاح عيب يبدأ باختبار يفشل قبل الإصلاح.
3. لا snapshots ضخمة لرفع التغطية؛ assertions تكون على الحالة والإحداثيات والرسائل والبكسلات المهمة.
4. mocks تطابق عقد Chrome/Konva ولا تعيد النجاح دائماً.
5. تُستخدم fake timers للمهل والمراقبين، مع إثبات إزالة listener/observer بعد كل نهاية.
6. اختبارات React تتعامل مع الواجهة كما يفعل المستخدم عبر role وlabel وkeyboard.
7. تُفصل اختبارات الوحدة السريعة عن E2E، لكن لا يُستبدل أحدهما بالآخر.
8. لا يُدمج ملف اختبار يرفع التغطية ويترك حالات flaky أو تحذيرات غير معالجة.

## 9. استراتيجية التعامل مع الكود صعب الاختبار

عندما يتعذر الوصول إلى فرع دون إعداد غير معقول، يكون القرار بالترتيب:

1. حقن dependency موجودة أصلاً مثل Chrome API أو clock أو decoder.
2. استخراج منطق نقي صغير إذا كان ذلك يحسن التصميم فعلاً.
3. اختبار العقد في Chromium الحقيقي.
4. توثيق أن الفرع غير قابل للوصول وإزالته إن كان دفاعاً ميتاً.
5. الاستبعاد هو الخيار الأخير، ويحتاج سبباً مسجلاً وتعويضاً واضحاً.

لا تُجرى إعادة هيكلة واسعة دفعة واحدة؛ كل استخراج يجب أن يبقى سلوكياً محايداً ويجتاز الاختبارات القائمة قبل إضافة اختبارات جديدة.

## 12. أوامر التحقق الإلزامية

```bash
npm run typecheck
npm run lint
npm run check:security
npm test
npm run test:coverage
npm run build
npm run test:e2e
```

عند إغلاق المرحلة النهائية يجب أيضاً:

- تشغيل `npm run test:coverage` من checkout نظيف.
- تشغيل E2E على `dist` المبني في نفس CI run.
- حفظ `coverage-summary.json` كـartifact.
- تشغيل المجموعة ثلاث مرات للتأكد من عدم وجود flaky tests.
- التأكد من أن `git diff --check` نظيف.
